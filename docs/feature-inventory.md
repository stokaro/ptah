# Feature-to-documentation inventory

This is the contributor-facing register of every public Ptah surface and the
page that owns its explanation. It exists so that a reader-facing gap is a row
someone can see rather than a discovery someone makes.

A public feature is **covered** only when a reader can find out what it does,
when to use it, how to invoke it, its important limitations, and where the exact
reference detail lives. A row in a generated command list is not coverage, which
is why this file records the page and the example separately from the command.

## Why this file is here and not on the site

It is a repository document at `docs/feature-inventory.md`, not a page under
`docs/site/src/content/docs/`. Three reasons, in the order they decided it:

- The audience is a contributor deciding where documentation for a surface
  belongs. `docs/site/CONTENT_INVENTORY.md` section 2 already fixes the split:
  the published site is canonical for everything reader-facing, and `docs/*.md`
  holds engineering references and check-script sources of truth. This file is
  the second kind — it is read by CI, and a reader looking for how to use
  `ptah schema apply` must land on the site page, not here.
- A site page needs a slug, a sidebar entry, and one of the page types the
  content inventory names. None of them fits a register whose rows are keyed by
  a machine. Giving it a sidebar entry would put a maintenance artifact in the
  reader's navigation, which is the thing the `documentation-map` retirement
  already decided against.
- `docs/agent-surface.md` is the precedent: a generated contributor register,
  living beside the guides, gated by a script.

One consequence, stated rather than discovered later: `docs/docs.go` embeds
`docs/*.md` into every Ptah binary, so this file ships inside `ptah` and the
`search_docs` MCP tool can answer from it. That is why its rows read as
statements about the product rather than as notes to a future editor.

## Maintenance rule

A change that adds, renames, or removes a public surface updates this file in
the same pull request. That includes a command or subcommand on either binary,
a value added to a `--to`, `--from`, `--format`, `--dialect`, or `--dir-format`
set, a `PTAH_*` variable, a schema input or export format, a dialect, a package
in `docs/public_api.md`, an OCI artifact or layer media type, an MCP tool, a
GitHub Action input or output, and a released artifact channel.

A row may not be deleted while its surface still ships. Retiring a surface means
deleting the surface and the row in one change.

`Last verified revision` moves forward only when someone re-runs the evidence.
Copying a claim from an older row is not verification, and a row whose evidence
was not re-run keeps the older revision even when the rest of the table moves.

## What the CI checks read

Each check keys on `Feature ID` and reads named columns. Editing a column
carelessly is what breaks them, so the mapping is written here rather than left
in the scripts:

| Check | Columns it reads | Fails when |
| --- | --- | --- |
| new public command with no entry | `Feature ID`, `Public surface` | a path the binaries answer has no `cli-*` or `cli-compat-*` row, or a row names a path no tree has |
| removed command still referenced by documentation | `Public surface` | a tracked `.md`/`.mdx` fenced block invokes a path no tree answers |
| documented flag that no longer exists | `Public surface`, and section 16's `Flag` and `Documented` columns | a fenced block passes a flag the command path it names does not register |
| public export or source format missing | `Feature ID` of the `fmt-in-*`, `fmt-out-*`, `gopkg-*`, and `bin-*` rows | a value the code accepts has no row |
| stale generated command reference | `Public surface` | a generated block disagrees with the tree it claims to render |
| quick-start commands that no longer run | none — it reads the pages | a quick-start command exits non-zero |

The sixth check is built: `internal/quickstart`, `scripts/check-quickstart.sh`
and `.github/workflows/quickstart-acceptance.yml`. It is referenced here rather
than duplicated, and the rows it covers name it in `Evidence`.

Only sections 1 through 16 hold machine-readable rows. The tables in this header
describe the format; they are not data.

reads column names rather than positions handles both, which is why the extra
column is inserted rather than appended.

### What a `Public surface` cell claims

A check reads the backticked tokens of that cell. Four spellings identify
themselves, and anything else in the cell is prose:

| Token | Kind | Example |
| --- | --- | --- |
| begins `ptah ` or `ptah-compat `, or is exactly one of them | a command path | `` `ptah schema render` `` |
| begins `go.5x5.cz/ptah/` | a package in the public-API ledger | `` `go.5x5.cz/ptah/dbschema` `` |
| begins `./` | a `main` package directory | `` `./cmd/ptah-ls` `` |
| `format:<list>/<value>` | one value of one enumerated set | `` `format:export-to/dbml` `` |

A format value needs the prefix because `sql` on its own names a file
extension, an inspect format and an export source at the same time. A row that
describes a flag rather than a command writes the flag without a launcher —
`` `schema export --to` `` — so it does not read as a command path that no tree
has.

Each `<list>` names one list in the code, and this is the mapping a format check
resolves against:

| List | Where the values are declared |
| --- | --- |

| `inspect-format` | `cmd/schema/inspect.go`, which spells the set three times |

## Evidence notation

The one rule: a cell says what was observed, never that a source was consulted.

| Token | Meaning |
| --- | --- |
| `tree(N)` | The path is one of N paths the built binary answers, from the walk in section 0. |
| `run: exit C, "..."` | The command was run at this revision from an empty directory with no `PTAH_*` variables set, and this is its status and first line. |
| `page: X names it N times` | A scan of tracked `.md`/`.mdx` found the exact invocation on that page N times. |
| `src:<path>:<line>` | Read in the tree at this revision. |
| `probe: ...` | A behavioral measurement with its own result stated. |
| `gate:<script>` | A CI gate that goes red when the claim stops holding. |
| `UNVERIFIED: ...` | Not established here. The cell says what would establish it. |

**`help` is not an evidence token, and that is deliberate.** Two measurements at
this revision say why. `--help` exits 0 on all 28 command paths that
`PTAH_ATLAS_STRICT_COMPAT=1` removes, including the four that answer
`unknown command`, so a presence probe built on it reports every removed path as
present. And on the seven `ptah-compat` commands that answer
`is not implemented by Ptah`, `--help` prints that one line and no flag block at
all while each command registers `--config`, `--env`, `--var` and `--help`, so a
flag census built on it under-reports. A command's own summary still supplies
`User goal`; what proves the row is in `Evidence` beside it.

## Stability values

| Value | Meaning |
| --- | --- |
| Stable | Registered on a released binary and expected to keep working. Ptah is pre-v1, so spellings, defaults and output may still change without a migration path; see the pre-v1 rule in `AGENTS.md`. |
| Preview | Shipped and usable, with the shape expected to change. Used only where the tree says so. |
| Compatibility-only | Exists to answer an Atlas contract and is reachable on `ptah-compat` only. |
| Compatibility-only (stub) | Registered so the tree matches, and refuses. Measured: exit 1, `ptah-compat <path> is not implemented by Ptah`. |
| Contributor tool | Builds from this module and is in no release. |

## 0. The revision, and how the command trees were measured

Everything below was measured against `master` at **8077bd1c0**
(`8077bd1c01c7329a8502394ee7a8573075fcecd7`), using binaries built from that
tree, whose `ptah version` reports the same commit. Where a claim was not
measured the cell says `UNVERIFIED` and what would settle it.

The document scans behind the `page:` and `Example` cells read the tracked
`.md` and `.mdx` files **at that revision**, listed by `git ls-files`. A page
this same change adds is therefore not counted, which is the point: the row
records the coverage the surface had before this work, so the next person can
tell what moved.

### 0.1 Two methods, run against each other

A census of a cobra tree can be taken two ways, and neither is trusted here
without the other.

- **Walk the built binary.** Run `<binary> <path> --help`, read the
  `Available Commands:` block, recurse. This is what a user meets.
- **Walk the tree in process**, after calling the two exported initializers
  `ExecuteC` calls before dispatch: `InitDefaultHelpCmd()` and
  `InitDefaultCompletionCmd()`.

| Tree | in process, as constructed | in process, after the initializers | built binary |
| --- | --- | --- | --- |
| `ptah` | 97 | 103 | **103** |
| `ptah-compat`, default | 52 | 53 | **53** |
| `ptah-compat`, `PTAH_ATLAS_STRICT_COMPAT=1` | 36 registered, 12 hidden | 37 registered, 12 hidden | **25 visible** |

Counts include the root. `ptah` is 1 root, 11 groups and 91 leaves; default
`ptah-compat` is 1 root, 6 groups and 46 leaves; strict `ptah-compat` is 1 root,
3 groups and 21 leaves.

### 0.2 The blind spot a census inherits, and why both numbers are printed

A walk over `cmd.Commands()` on a **constructed** root cannot see `completion`
and `help`, because cobra adds them in `ExecuteC`. Measured on `ptah`: 97
against 103.

The cause is not the same on the other binary. `installAtlasCompletionCommand`
calls `InitDefaultCompletionCmd()` at construction, so the constructed
`ptah-compat` tree already carries `completion` and its four shells and is short
by one path, not six. A check that knows only "cobra hides six" is right about
`ptah` and wrong about why; a check that measured only `ptah-compat` in process
would conclude the gap is one path. That is why the table above prints both.

This is not hypothetical. `docs/agent-surface.md` is generated by
`internal/cmd/agentsurface`, which walks the constructed root, and is gated by
`scripts/check-agent-surface.sh` in `go-lint.yml`. Measured at this revision its
generated block holds **86 rows against the tree's 91 leaves**, and the string
`completion` appears **0 times** in the whole file. The gate is green.

### 0.3 The one exemption, and what polices it

`ExecuteC` also calls the unexported `initCompleteCmd`, which registers the
hidden `__complete` and `__completeNoDesc` commands. Neither walk can reach
them: they appear in no `--help` output, and the initializer that adds them
cannot be called from outside cobra. They ship and they answer — measured,
`ptah __complete ""` and `ptah __completeNoDesc ""` both exit 0 on all three
profiles, and `ptah --help` mentions neither.

They are therefore exempt **by name**, two literal strings, with this sentence
as the reason. Nothing else is exempt: `completion`, `help` and the four shells
are all reachable through the exported initializers, so exempting them would be
choosing the weaker of two available answers. What polices the exemption is that
a walker must assert those two are the only paths the binary answers that the
walk did not produce — a third one fails rather than joining the list.

### 3. Configuration files and environment variables

`PTAH_*` names come from three sources that do not overlap cleanly, and no one
of them is the surface. Measured at this revision: **197** names are derived
from a registered flag and carry an `[env: PTAH_...]` marker in that flag's own
help; **2 more** are derived from a hidden flag and appear in no help at all;
**24** are registered boolean toggles; **31** are non-boolean names written as
literals. The union is **242**. Of the 24 booleans, 2 are also flag-derived; of
the 31 literals, 10 are also flag-derived and 21 are reachable only as a
variable.

A grep-based census sees almost none of this: 194 of the flag-derived names
never appear as a string literal anywhere in the tree, because
`cmdflags.EnvName` computes them from the flag name.
