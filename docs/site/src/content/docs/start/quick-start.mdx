These quick starts cover schema changes. Ptah reads a live database, works out
how it differs from the schema you want, and changes it through migration files
you keep in your repository or through a direct apply.

To replace an embedding model or preprocessing contract without overwriting
active vectors, use [Inference migrations](../../inference/overview/).

Which of those two you try first is the only decision on this page.

Neither is a reduced form of the other, and a project can use both. If the
choice matters more than five minutes of reading, [Choose a
workflow](../choose-a-workflow/) sets out what each one costs and what it buys.

## What both quick starts need

- A `ptah` binary on your `PATH`. [Install Ptah](../install/) covers the routes.
- A terminal. Both Bash and PowerShell are shown on each page.
- About five minutes.

Both run against a local SQLite file, so neither needs a database server, a Go
toolchain, or Docker. Both end by deleting the one directory they created.

## What the quick starts leave out

Each page runs one path so that it stays short. Three things they do not cover
are worth knowing exist:

- **The other schema sources.** The direct quick start uses plain SQL. Ptah
  reads the desired schema from YAML, HCL, and DBML files, from an external
  loader, and from annotated Go structs, and every source parses into the same
  internal representation. Go is one source among several, not the entry point.
  See [Work with a desired schema](../../schema/work-with-a-source/).
- **Migrations Ptah writes for you.** The two workflows meet at
  `ptah migrations generate`, which turns the difference between a desired
  schema and a live database into an ordinary migration pair. See
  [Generate migrations](../../versioned/generate/).
- **Engines other than SQLite.** The same commands take a PostgreSQL, MySQL, or
  other supported database URL in place of the SQLite one. What each engine
  accepts differs. See the
  [database support matrix](../../databases/support-matrix/).
