### Components

| Component | Responsible for | Understands | Does not own |
| --- | --- | --- | --- |
| Ptah Core (Host: the ptah binary) | Loads the declaration, compares common tables, routes provider models to their owners, orders the whole plan, prints and applies it. | Common tables, identities and coverage. A provider payload only as bytes. | What a transfer means, or whether its source will exist after the plan. |
| Contract and SDK (Boundary between Core and the provider) | Defines the messages and features both sides agree on. The SDK checks each request and answer against them. | Message shapes, identities, representations and coverage records. | YDB meaning: a well-formed request can still describe a plan YDB would refuse. |
| YDB provider (Provider: the ptah-plugin-ydb executable) | Reads the YDB catalog, compares the models it owns, proposes plan steps, renders and runs YQL. | YDB semantics: changefeeds, topics, transfers and what each one needs. | Common tables, the order of the whole plan, and migration history policy. |
| YDB server (The database) | Stores the tables, keeps the changefeed and its topic, and runs the transfer after Ptah exits. | YQL statements and its own catalog. | The declaration, the comparison and the plan. |

### Workflow steps

| Step | Who acts | What happens | Result in a normal creation |
| --- | --- | --- | --- |
| 1. Declaration | Ptah Core, Contract and SDK, YDB provider | Core loads schema.yaml. The provider decodes the YDB extensions, the changefeed and the transfer, and the SDK checks their values. | The declared tables in Core's common model, and normalized values of the changefeed set and the transfer. |
| 2. Selection | Ptah Core, Contract and SDK, YDB provider | Core starts the provider and asks what it serves. Both agree on features, such as models.current-context, and the provider opens a session. | A session on the database and the list of features both sides negotiated. |
| 3. Reading | Ptah Core, YDB provider, YDB server | The provider reads the selected directory, shop, and says what it established about each kind. | Nothing in shop, and coverage that says shop was read completely. |
| 4. Comparison | Ptah Core, Contract and SDK, YDB provider | Core compares the common tables and sends each owner a request. ydb-transfers receives the declared transfer with the facts it needs about other owners. | A request with both tables in declaredRelations and the changefeed in declaredFacets. |
| 5. Changes or refusal | YDB provider | Each owner returns changes or refuses one and says why. ydb-transfers checks the transfer's source and target first. | Two new tables from Core, a new changefeed from ydb-row-table-properties and a new transfer from ydb-transfers. |
| 6. Planning | Ptah Core, Contract and SDK, YDB provider | The provider turns its changes into steps and says which steps depend on which. Core checks them and orders the whole plan. | Four operations, the transfer last, after its changefeed and both tables. |
| 7. Review and execution | Ptah Core, YDB provider, YDB server | Core prints the plan. On apply, the provider renders YQL and runs it, and YDB starts the transfer. | The statements run, and a row written to orders reaches orders_archive. |
| 8. Reinspection | Ptah Core, YDB provider, YDB server | The next run reads and compares again. | Schema is synced, no changes to be made. |

### Scenarios

| Scenario | Changed fact | Decided by | Outcome |
| --- | --- | --- | --- |
| Normal creation | Every object is declared, and shop is empty. | Each owner reports its own changes; Core orders them. | Four operations; the transfer is created last. |
| Valid no-op | Every object is declared, and the database already holds all four as declared. | ydb-transfers runs its dependency checks, and they pass. | Schema is synced, no changes to be made. |
| Missing source | The schema leaves out the changefeed feed of orders, and the database has none. | ydb-transfers, before anything is planned. | Refused: the transfer reads a topic the plan leaves absent. |
| Unrepresentable source, current context | The tables exist, and orders holds a changefeed whose consumer names a codec Ptah does not declare. The schema leaves the changefeed out. The host and the provider negotiate models.current-context. | ydb-transfers, from the current context. | The transfer is created; the plan neither drops nor changes the changefeed. |
| Unrepresentable source, no current context | The same database and schema, with a host or a provider that does not negotiate models.current-context, such as Ptah v0.24.1 or YDB plugin v0.7.0. | ydb-transfers, without the read's facts about changefeeds. | Refused as a transfer of a missing topic. |
