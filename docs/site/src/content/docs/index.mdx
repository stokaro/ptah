Ptah is a command-line tool for database schema management. It reads the schema
you want, reads the schema a live database has, and works out the difference
between them. You choose what happens next: record the difference as versioned
migration files, or apply it to the database directly. One project can do both.

1. **Schema sources or a live database.** Ptah reads the schema you want from
   SQL, YAML, HCL, DBML, an ORM loader, or Go annotations. It also reads the
   schema a running server already has. See
   [Work with a schema source](./schema/work-with-a-source/).
2. **Desired schema.** Every source parses into the same model, so the stages
   after this one behave the same whichever format you wrote. Several sources
   can be merged into one desired schema.
3. **Inspect, compare, plan.** Ptah reports what the database contains,
   compares it with the desired schema, and produces the SQL that would close
   the gap. See [Compare and detect drift](./direct/compare-and-drift/).
4. **Versioned migrations or direct apply.** Write the change into timestamped
   migration files that you review and commit, or apply it to the database in
   one step. See [Versioned migrations](./versioned/overview/) and
   [Apply a schema directly](./direct/apply/).
5. **Database.** Both routes reach the same server. The versioned route also
   records which versions are applied, and `ptah migrations status` reads that
   record back.

## Two workflows, and how to combine them

### Versioned migrations

You own a directory of SQL files. Ptah creates them, protects them with an
integrity file, applies them in version order, and rolls them back.

```bash
ptah migrations create create_users --migrations-dir ./migrations
ptah migrations hash --dir ./migrations
ptah migrations up --db-url "$DATABASE_URL" --migrations-dir ./migrations
ptah migrations status --db-url "$DATABASE_URL" --migrations-dir ./migrations
```

### Direct schema changes

The change reaches the database now, with no migration file in between. Ptah
works out the SQL that closes the difference, applies it once you approve the
plan, and tells you when the database has moved away from the schema you want.

```bash
ptah schema compare --db-url "$DATABASE_URL" --schema-file schema.sql
ptah schema apply --db-url "$DATABASE_URL" --schema-file schema.sql
ptah schema drift --db-url "$DATABASE_URL" --schema-file schema.sql
```

### Both at once

Keep the schema description as the thing you edit, and let Ptah turn each
change into reviewable migration files. One command bridges the two workflows.

```bash
ptah migrations generate --db-url "$DATABASE_URL" --schema-file schema.sql \
  --migrations-dir ./migrations --name create_users
```

[Choose a workflow](./start/choose-a-workflow/) sets out which combinations
exist and what each one costs.

## What the project includes

Ptah is published under the MIT license. Migration integrity, deterministic
planning, drift detection, approvals, advisory locking on the engines that
provide it, recovery, testing, and artifact distribution are all part of the
same open-source project. Deterministic means that the same inputs produce the
same SQL on every run.

The [database support matrix](./databases/support-matrix/) lists every engine
Ptah supports, the dialect name and URL scheme each one uses, and how deep the
support goes.

The CLI runs on its own and needs no Go toolchain. Go projects can also embed
Ptah through its [documented Go packages](./extend/public-api/), use
[Go annotations](./schema/go-annotations/) as one of the schema sources, and
run the `ptah-ls` language server for annotation support in an editor.

## Atlas compatibility

A separate `ptah-compat` binary presents an Atlas-compatible command surface for
scripts written against the Atlas CLI. The
[Atlas compatibility overview](./atlas/overview/) explains what it covers and
where it differs. The native `ptah` binary has no Atlas command spellings.

## The name

Ptah is named after the Egyptian god of architects and craftsmen. The four
stages the name stands for are the ones the diagram above walks through:
**Parse** a schema source, **Transform** it into the change the database needs,
**Apply** that change, and **Harmonize** the result with the schema you declared.
